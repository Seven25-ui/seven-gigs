How to Build Static Blog Pages Automatically With GitHub Actions

Nov 16, 2026 · 4 min read

If your blog loads posts with JavaScript from a database, visitors see the content, but some search engines and social media tools may not see it as easily. A simple fix is to create a real HTML page for each post. Doing that by hand for every new post is boring, so you can automate it with GitHub Actions. This guide explains the idea and the basic setup.

The problem

Imagine a blog where the posts live in a database and the home page loads them with JavaScript. The page itself is almost empty until the script runs. A visitor in a browser sees everything, but a crawler or a link preview tool may only see the empty page. If every post also has its own static HTML file with a title, a description, and the full text, those tools can read it without running any script.

The idea

A small Node script does four jobs:

1. It reads your published posts from the database
2. It writes one HTML page per post into a folder such as posts
3. It writes a sitemap.xml file with all page addresses
4. It writes a robots.txt file that points to the sitemap

GitHub Actions then runs the script for you, on a schedule and whenever you change the script, and saves the new files back into your repository.

Step 1: Write the script

Keep the script simple and put it in a folder such as scripts. It should read the public address and the public (anon) key of your database, request only published posts, and create the files. Create a safe slug from each title, for example how-to-use-upwork-connects-wisely, and use it as the file name. Add a canonical link and a description to every page.

An important safety rule: use only the public anon key, and protect your data with access rules in the database, so the key can only read published posts. Never put an admin or service role key in a public repository.

Another safety rule: if the database returns zero posts but pages already exist, stop the script instead of deleting everything. A temporary error should never wipe your pages.

Step 2: Create the workflow file

In your repository, create the folder .github/workflows and add a file such as build-posts.yml. A simple version looks like this:

name: Build post pages

on:
  schedule:
    - cron: "23 */6 * * *"
  workflow_dispatch:
  push:
    paths:
      - ".github/workflows/build-posts.yml"
      - "scripts/build-posts.mjs"

permissions:
  contents: write

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: node scripts/build-posts.mjs
      - name: Commit changes
        run: |
          git config user.name "github-actions[bot]"
          git config user.email "41898282+github-actions[bot]@users.noreply.github.com"
          git add -A posts sitemap.xml robots.txt
          if git diff --cached --quiet; then
            echo "No changes to commit"
          else
            git commit -m "Update post pages"
            git push
          fi

What the parts mean

- schedule runs the job at regular times. The times use UTC, so they may not match your local time.
- workflow_dispatch adds a Run workflow button in the Actions tab, so you can run it manually.
- push runs the job once when you change the workflow or the script.
- permissions allows the job to save the new files in your repository.
- The last step commits files only when something changed.

Step 3: Allow the Action to write

In your repository, open Settings, then Actions, then General, and check the workflow permissions. The job must be allowed to write to the repository, or the push step will fail.

Step 4: Run it and check

Open the Actions tab, choose your workflow, and click Run workflow. A green check means it worked. Open the posts folder in your repository and look for the new HTML files. Then open one of them on your live site and check the title, the text, and the links.

Step 5: Keep working normally

When you publish a new post, the home page shows it right away. The static page appears the next time the Action runs. If you want it faster, press Run workflow.

Useful tips

- Test your script locally with a small sample file of fake posts before you use real data
- Pull the latest changes before you edit your repository on your computer, because the Action also makes commits
- Keep the same slug for a post after you publish it, so links do not break
- Update the sitemap address in the script if you change your domain

Final thoughts

This setup is small, but it teaches an important automation pattern: a trigger starts a job, the job collects data, creates files, and saves the result. Once you understand it, you can use the same pattern for reports, backups, and many other tasks.
