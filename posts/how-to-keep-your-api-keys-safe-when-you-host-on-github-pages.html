How to Keep Your API Keys Safe When You Host on GitHub Pages

Nov 12, 2026 · 4 min read

GitHub Pages is a great free way to host a website, but it comes with one important rule: everything in a public repository can be read by anyone. That includes your HTML, your JavaScript, and any keys you place inside them. Many beginners accidentally publish secret keys and only notice later, when someone abuses them. This guide explains what is safe, what is not, and how to protect yourself.

1. Understand what "public" really means

When your repository is public, anyone can open your files and read them. Even if your site hides something visually, the code behind it is still visible. So the question is not "can people find my key?" but "what happens if they do?"

2. Know the difference between public and secret keys

Some keys are designed to be used in the browser. For example, many services give you a public or anonymous key that is meant for front-end code. These are only safe when the service has proper access rules in place. In Supabase, for instance, the public key is only safe when Row Level Security is turned on and your policies are correct. Without those rules, someone could read or change data they should not.

Other keys are secret. These include service role keys, private API keys, payment keys, and AI provider keys. A secret key should never appear in front-end code or in a public repository.

A simple test: if the key can delete data, spend money, or act as an admin, it must stay secret.

3. Turn on access rules for your database

If your site talks directly to a database, set up rules that decide who can read and write. Allow public reading only for the data that really is public, such as blog posts. Keep writing limited to logged-in admins. Test these rules by trying to do something you should not be able to do.

4. Use a small backend or proxy for secret keys

If your website needs an AI model or another paid service, do not put that key in your JavaScript. Instead, create a small server function, such as a Cloudflare Worker, that holds the key and talks to the service for you. Your website sends a request to the Worker, and the Worker adds the secret key on the server side. The browser never sees it.

Store the key as a secret or environment variable in the platform, not inside the code file.

5. Keep secret files out of your repository

Create a file named .gitignore and list files that should never be uploaded, like .env files. This tells Git to skip them. Do this before your first commit, because it is easier to prevent a leak than to clean one up.

6. Add limits where you can

Many services let you restrict a key so it only works from your website address, or only for certain actions. Turn on these limits. Also set usage or budget limits so a leak cannot cost you a lot of money.

7. What to do if a key leaks

Act quickly:

- Revoke or rotate the key in the service dashboard right away
- Create a new key and update your project
- Check usage logs for strange activity
- Remember that deleting the key from your file is not enough, because the old version stays in the history

Treat any key that has been public as compromised, even if you removed it a minute later.

8. Watch for warnings

GitHub can warn you when it detects certain secrets in a repository. If you receive such an alert, take it seriously and follow the steps above immediately.

A quick safety checklist

- No secret keys in front-end code
- Database rules turned on and tested
- Secret keys stored on the server side
- .env files ignored by Git
- Limits and budgets set on paid services
- A plan ready to rotate keys

Final thoughts

You do not need to be a security expert to stay safe. You only need a few good habits: keep secrets on the server, use public keys only with proper rules, and react fast when something goes wrong. These habits protect your projects, and they also show clients that you build things carefully.
