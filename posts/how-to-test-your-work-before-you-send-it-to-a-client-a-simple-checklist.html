How to Test Your Work Before You Send It to a Client (A Simple Checklist)

Nov 23, 2026 · 4 min read

One bug in a delivered file can cost you a review. Testing before you send takes only a few minutes, and it is one of the cheapest ways to look professional. Here is the checklist I use, with a real example from my own work.

1. Test on fake data, never on real client data

Before I run a script on anything important, I make a test folder with fake files. If something goes wrong, nothing real is lost. For a file renaming script, I created three fake text files and one file of a different type that should not change.

2. Check the exact request

Reread the job post and write the requirements as a short list. For my renaming script the list was: rename only the .txt files, use numbers like file_001.txt, keep the extension, and never overwrite anything. After the test, I checked each line one by one.

3. Test the normal case and the edge case

The normal case is the usual one. The edge case is the one clients forget to mention. What happens if two files already have the target name? What if the folder is empty? What if the names have spaces? You do not need to test everything, but pick two or three edge cases.

4. Run it twice

A script that works once but breaks on the second run is a common problem. After my test, I ran the script a second time to make sure nothing was lost or overwritten.

5. Compare before and after

Look at the files before and after. In my test, the three text files were 13 bytes each before the script and 13 bytes each after it, and the extra file stayed at 16 bytes. The same sizes told me the contents did not change. A simple before-and-after check catches many mistakes.

6. A real example, step by step

Here is how the checklist worked on my own test. I wrote four requirements. I made a fake folder with three .txt files and one .md file. I ran the script and it reported three renamed files. I looked at the folder: the names were file_001 to file_003, and the .md file was untouched. Then I ran the script again and checked that nothing was lost. The whole test took only a few minutes, and now I can send the script with confidence.

7. Think about the client's computer

If you work on Windows and your client uses a Mac, mention it. Paths, line endings, and installed tools can be different. When you cannot test their setup, say so honestly and write clear instructions for running the work.

8. Write simple instructions

Many clients are not technical. Three short steps are better than one long paragraph. Include the exact command they should copy. If you can, follow your own instructions from a fresh folder to check that they work.

9. Keep a copy of what you sent

Save the exact version you delivered. If the client comes back with a question, you can open the same file and see what they see.

10. Do not trust AI code blindly

If you use an AI tool to help you write code, test it even more carefully. AI can be wrong in small ways that look right. The tool helps you start, but you are responsible for the final result.

11. A checklist you can copy

- I wrote the requirements as a list.
- I tested on fake data.
- I tested the normal case and two edge cases.
- I ran it twice.
- I compared before and after.
- I wrote simple instructions and tried them myself.
- I saved a copy of what I sent.

12. What to tell the client when you deliver

Keep the message short and clear. Say what the file does, how to run it, and what you tested. For example: "I tested this on a sample folder, including a second run, and it works as described. Please make a backup copy before using it on your real files." This shows care and protects both of you.

Testing does not make you slower. It makes your delivery calm, and calm deliveries lead to good reviews.
